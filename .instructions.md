# Agent Standards

## Non-Negotiable User Directives

- Do not make unverified assumptions about user intent, UI changes, environment state, network setup, or desired scope.
- Treat bridge/IP/live-memory work as the active scope unless the user explicitly expands scope.
- Do not redesign, replace, or simplify the UI shell unless the user explicitly asks for UI changes.
- When a fact is not confirmed by the user, the repo, or direct tool output, state that it is unconfirmed instead of assuming it.
- When a missing fact would materially change code edits, pause and ask one concise question instead of guessing.
- The confirmed Windows UI address for this repo is `http://10.0.0.25:3000` until the user says otherwise.
- The confirmed Steam Deck bridge target for this repo is `BRIDGE_TARGET_HOST=10.0.0.25` and `BRIDGE_TARGET_PORT=32840` until the user says otherwise.
- Primary runtime target for user-directed validation is `http://10.0.0.25:3000`; do not switch to isolated test endpoints unless the user explicitly asks for backend-only verification.
- Do not change anything besides what the user explicitly requested to be changed.

## Fact-Checking Before Conditionals

**CRITICAL RULE:** Never use conditional language ("if", "check if", "verify that") when providing instructions if the context or conversation history has already definitively established the fact.

**Examples:**

❌ WRONG:
```
If the env file shows BRIDGE_TARGET_HOST=10.0.0.1, run:
printf "BRIDGE_TARGET_HOST=10.0.0.25..."
```

✅ CORRECT:
```
Run this:
printf "BRIDGE_TARGET_HOST=10.0.0.25..."
```

When something is known to be true from prior context, state it as fact. Remove all speculative conditionals.

## Code Block Format

- Always provide plain copy-paste code blocks
- Always use fenced code blocks for commands and scripts so users can copy-paste directly
- Format: "Run this in (program) on (device):\n\n[code]"
- No explanatory prose around the code
- No markdown formatting within code blocks that could cause copy-paste issues
- Always provide explicit step-by-step run instructions before command blocks.
- Always provide the full runnable command text.
- If a command requires a specific directory, always include an explicit `cd` to that directory before running it.
- Use this command response schema for runnable commands:
	1. Step N title line
	2. One fenced code block containing only runnable commands
	3. First line in the block must be `cd` to the required directory when directory context matters
	4. No inline commentary inside code blocks
- For every technical response, run a drift check against README MVP sections before answering:
	1. `MVP Outline Status`
	2. `Shortest Path To Live UI Readback`
	3. Reject additions that are not required to advance those sections or the active user request
- Compliance gate: if a response would violate these formatting rules, stop and ask one concise clarification question instead of proceeding.

## Instruction Precision

- Be direct and specific
- Use only confirmed facts from conversation history
- Do not add hedging language
- Do not make assumptions about user's environment state
- Automated backend verification data must use isolated non-primary ports only.
- Automated backend verification data must not surface in the UI or debug panels.
- Automated backend verification data is for development only and is never live bridge truth.
- User UI and debug panels must never show test data under any circumstance.
